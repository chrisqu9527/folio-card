# MCP 与网页维护方案

目标：在网页新增或编辑风格，AI 客户端读取同一份已发布数据，网站、MCP 和 Skill 的编号、原文、来源一致。

## 第一版选择

目前规模适合继续用 GitHub 管理主数据，不急于引入数据库。管理员后台通过服务端调用 GitHub API，把主数据、生成文件和新封面作为一个提交保存，保留完整修改历史。前端不持有 GitHub 凭证。多管理员协作或大量上传出现后，再迁移为数据库和对象存储；稳定编号与 id 保持不变。

后续上线时，将网页和 MCP 查询改为读取统一发布 API。该 API 读取 main 已发布的主数据，返回提交 SHA 作为版本号，支持 ETag／短缓存；网页发布后失效缓存。已经安装到本地的 Skill 是快照，需要显式更新或使用 MCP，不能声称本地文件会自动变化。

## MCP 读取接口

远程提供 `/mcp`，使用 Streamable HTTP；本地可另提供 stdio。用官方 SDK 实现握手与工具协议。

| 工具              | 输入与行为                                                     |
| ----------------- | -------------------------------------------------------------- |
| `get_prompt`      | 编号，返回原文、样图 URL、作者、来源和数据版本                 |
| `search_prompts`  | 关键词、媒介、风格分类、视频用途、分页；返回摘要，按需读取全文 |
| `list_categories` | 返回风格分类、视频用途和数量                                   |
| `render_template` | 编号和明确的槽位值；仅替换已声明槽位，保留原文及来源           |

首版 MCP 提供查询。写入先放在网页登录后的后台，减少编号分配和并发发布入口。需要 Agent 自动维护时，再给写工具增加管理员授权、预览和独立发布步骤。

## 网页更新流程

管理员登录 → 填写原文、来源、作者、分类、槽位、模型备注 → 上传样图 → 预览 → 发布。创建时服务端分配下一个稳定编号；根据源码中的稳定 id 编辑已有条目，不允许修改编号。已发布内容可下架，但编号不回收。

发布服务核对管理员身份、完整字段、编号／id／来源重复、封面和生成文件，然后使用读取时的提交 SHA 检查并发变化；遇到版本冲突返回清楚的重载提示。完成后读取回发布提交验证内容，失效查询缓存。回滚内容也要保留后续已分配的编号，避免重新使用旧号。

所需配置：网站及 MCP 的部署地址、管理员登录、仅服务端持有的仓库写凭证（优先 GitHub App 的仓库级 contents 权限）。本次版本统一不需要这些新配置；实际部署后台时再接入。

## 验收标准

网页新增一条后，网站检索与 MCP 返回相同编号和原文；非法管理员写入被拒绝；同时发布不覆盖别人修改；回滚不改变编号；Skill 导出可通过 `data:check`；服务重启或重新部署后发布内容仍存在。
